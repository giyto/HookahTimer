## Context

Первый change уже реализовал однопроцессное состояние зала: `HallViewModel` владеет списком `HallTable`, а Compose отправляет ему действия и отображает `StateFlow`. Для мотивации второго этапа см. `proposal.md`, а пользовательский контракт описан в `specs/table-settings/spec.md`.

Настройки должны работать на планшете, не смешивать временно некорректный ввод формы с корректной моделью стола и не вводить временный формат постоянного хранения перед Room. Нажатия на стол в рабочем режиме зарезервированы для будущего change таймеров.

## Goals / Non-Goals

**Goals:**

- Расширить модель стола валидной упорядоченной конфигурацией проходок.
- Изолировать черновик формы и её валидацию от сохранённого состояния зала.
- Сохранить существующий MVVM/UDF-подход и единственного владельца списка столов.
- Сделать переходы и форму удобными для сенсорного планшета и проверяемыми unit/UI-тестами.

**Non-Goals:**

- Не запускать и не отсчитывать таймеры проходок.
- Не добавлять Room, repository-слой, сериализацию или восстановление после завершения процесса.
- Не добавлять изменение порядка проходок, секунды или предустановленные шаблоны времени.
- Не менять правила добавления, перемещения и удаления столов первого change.

## Decisions

### 1. Валидная доменная конфигурация отдельно от черновика формы

`HallTable` получит упорядоченный список конфигураций проходок. Каждая проходка имеет стабильный UUID и положительную длительность в целых минутах; фабрика значений по умолчанию создаёт две проходки по 30 минут. Стабильный идентификатор не зависит от отображаемого порядкового номера и позволит следующему change связывать таймерное состояние с конкретной проходкой.

Черновик настроек хранит название и длительности как строки, потому что во время ввода поле законно бывает пустым или временно некорректным. Только успешная валидация преобразует черновик в доменную конфигурацию. Альтернатива — сразу записывать каждое нажатие клавиши в `HallTable`; она допускает некорректные промежуточные данные и делает отмену сложной.

### 2. Отдельный `TableSettingsViewModel` для формы

Экран настроек использует собственные `TableSettingsUiState`, события и `StateFlow`. ViewModel создаёт черновик из выбранного стола, выполняет локальные изменения, добавление/удаление проходок и выдаёт валидный результат только по действию сохранения.

`HallViewModel` остаётся единственным владельцем сохранённого списка столов и атомарно заменяет конфигурацию выбранного стола после успешного сохранения. Отмена удаляет экран настроек вместе с черновиком и не отправляет обновление. Альтернатива — поместить все поля открытой формы в `HallUiState`; она связывает жизненный цикл формы с рабочим полем и усложняет тестирование независимых переходов.

### 3. Navigation Compose и передача только идентификатора стола

Корневой Compose-контент получит `NavHost` с маршрутами зала и настроек, а `HallViewModel` останется scoped к Activity и будет передан обоим маршрутам. В аргументе маршрута передаётся только UUID стола; сериализовать весь `HallTable` в route нельзя, иначе появляется вторая копия состояния и риск сохранить устаревшие данные.

В режиме редактирования обычное нажатие на тело стола открывает настройки, а drag продолжает перемещение после превышения порога жеста. Отдельная кнопка удаления сохраняет существующее поведение. В рабочем режиме обработчик открытия настроек не подключается. Если стол с указанным UUID отсутствует, маршрут безопасно возвращается в зал без создания данных.

Альтернатива — диалог поверх зала. Она тесна для переменного списка проходок и хуже использует пространство и клавиатуру планшета.

### 4. Явные сохранение и отмена

Кнопка сохранения сначала проверяет обрезанное название, наличие хотя бы одной проходки и преобразование каждой длительности в положительный `Int`. Ошибки хранятся рядом с соответствующими полями. При любой ошибке исходный стол не меняется; при успехе все поля применяются одной операцией и навигация возвращается в зал.

Системное действие Back и явная отмена имеют одинаковую семантику: закрывают маршрут без обновления `HallViewModel`. Это предсказуемее автосохранения, при котором частично введённое значение могло бы незаметно изменить рабочий стол.

### 5. Поведение списка проходок

Новая проходка добавляется в конец с UUID и длительностью `30`. Удаление доступно только при размере списка больше одного. Отображаемый номер вычисляется по позиции, поэтому после удаления не остаются разрывы, а стабильные UUID остальных элементов не меняются.

Изменение порядка не включается: таймерный change сможет добавить его отдельно, если практика покажет необходимость. Хранить только количество проходок и отдельный массив длительностей отклонено, поскольку это не даёт стабильной идентичности элементам.

### 6. Адаптация формы под планшет

Экран строится на Material 3 `Scaffold` с верхней панелью, явными действиями отмены/сохранения и прокручиваемой формой ограниченной ширины. Поля и кнопки имеют сенсорные зоны не меньше стандартного Material-размера; выбор формы отображает два понятных варианта, а длительность использует цифровую клавиатуру и подпись «мин».

Ограниченная ширина сохраняет читаемость на большом планшете, а вертикальная прокрутка поддерживает длинный список проходок и открытие экранной клавиатуры.

### 7. Состояние только в живом процессе

`HallViewModel` переживает пересоздание Activity. `TableSettingsViewModel`, привязанный к back stack entry, сохраняет черновик при повороте, пока процесс жив; состояние навигации восстанавливает открытый маршрут. `SavedStateHandle` и постоянное хранение не добавляются, потому что Room будет отдельным change и станет единым форматом восстановления.

### 8. Проверка на трёх уровнях

Unit-тесты модели проверяют значения по умолчанию и инварианты конфигурации. Unit-тесты формы покрывают изменение полей, добавление/удаление, ошибки и атомарный результат сохранения. Тесты `HallViewModel` подтверждают обновление только выбранного стола и сохранение позиции.

Compose UI Tests проверяют открытие только из режима редактирования, отображение исходных данных, ошибки, отмену и успешное применение названия/формы/проходок. Инструментальный тест поворота проверяет сохранение незавершённого черновика.

## Risks / Trade-offs

- [Сохранённые настройки теряются после завершения процесса] → Оставить ограничение явным и подключить Room отдельным change до рабочего использования.
- [Длинный список проходок не помещается на экран] → Использовать прокручиваемый список и закреплённые действия верхней панели.
- [Tap для настроек конфликтует с drag] → Использовать порог drag и открывать настройки только после завершившегося без перемещения tap-жеста.
- [Изменение круга на pill меняет допустимую область позиции] → Сохранить нормализованную позицию и повторно ограничить отображение по фактическому размеру новой формы.
- [Длительность выходит за диапазон `Int`] → Считать неразбираемое или переполненное значение ошибкой формы и не сохранять его.

## Migration Plan

1. Добавить Navigation Compose и модели конфигурации с безопасными значениями по умолчанию для всех создаваемых столов.
2. Расширить `HallViewModel` атомарным обновлением настроек выбранного стола.
3. Добавить состояние, ViewModel и Compose-экран формы настроек.
4. Подключить навигацию и открытие настроек из редакторского режима зала.
5. Добавить тесты и проверить сборку на эмуляторе и реальном планшете.

Откат состоит в удалении маршрута настроек и полей проходок и возврате прежней фабрики `HallTable`; постоянные данные и миграции базы отсутствуют.
